# 전투 프레임 · 알고리즘 · 삽화 전용 (2026-11-19)

사용자 목표: **전투 중 프레임 저하 해결 · 전투 알고리즘 고도화 · 삽화 방식만 쓰고 다른 방식은 업데이트 없이 모두 끄기.**
버전 **1.1e / code 36** 로 로컬 커밋 · APK 빌드까지 했다. 푸시 · 서버 배포는 하지 않았다. Android 기기 실측도 없다 (기기 연결 불가 —— 1.1e APK 로 확인).

## 1. 삽화 전용 —— 다른 방식 끄기

코드는 지우지 않고 스위치 하나로 끈다. 되살리려면 `Settings.PAINTING_ONLY = false`.

| 끈 것 | 어디서 |
|---|---|
| 화풍 고르기(전쟁 삽화 / 기존 군집) · 3D · 수묵 · 점묘 | `Settings.PAINTING_ONLY` —— 불러올 때 · 적용할 때 타입2 + 삽화로 고정, 설정 화면 선택칸 숨김, 점검 인자 `--gtype2 --gsumuk --gdots --dots` 무시 |
| 3D 병사 · 무기 · 깃발 · 발밑 고리 · 진지 · 지형 메시 · 나무 만들기 | `War3D.no3d` (setup) |
| 3D 입자(CPUParticles3D —— 상태 기운 · 등급 기운 · 먼지 · 불꽃) · 점광 · 고리 · 데칼 | `War3D.no3d` (`_particles` · `_light` · `_ring` · `step`) —— 보이지 않는데 CPU 가 계속 시뮬레이션했다 |
| GPU 군집 값 줄(`_sq_tex`) 매 프레임 올리기 · 3D 카메라 | `War3D.no3d` (`step` · `_process_inner`) |
| 옛 군집용 병사 객체(전투마다 만 명 넘게) 만들기 · 쓰러뜨릴 병사 고르기 | `Squad.lite` —— 아래 카드의 '○○명'은 같은 식으로 세기만 한다 |

삽화 화면이 실제로 쓰는 것(부대 위치 · 상태 재생, 고유기 예약, 밀림 → hurt)은 그대로 돈다.

## 2. 프레임

측정: `tests/motion5_replay -- --secs=15 --skip=3` (PC, Vulkan Mobile 렌더러, 400×800, 9 대 9, 시드 5100). **Android 실측이 아니다.**
구간별 CPU 는 같은 실행의 `cpu_ms_per_frame` (`--phase-cpu` 면 행군 · 교전 · 고유기 구간별).

| | 평균 | p95 | p99 | 최대 | 고유기 구간 p95 | 그리기 호출 | 삽화 · HUD 갱신 |
|---|---:|---:|---:|---:|---:|---:|---|
| 고치기 전 (1.1c) | 6.47ms | 11.98 | 16.48 | 20.64 | 15.44 | 700 | 30Hz (부하 4단계로 시작) |
| 고친 뒤 | 4.20ms | 6.18 | 7.61 | 9.88 | 6.75 | 580 | **60Hz** (부하 0단계) |

고치기 전 수치는 삽화 · HUD 가 30Hz 로 돌던 값이다 —— 옛 군집 병사 수(계산 15,580명)로 부하 단계를 처음부터 4 로 잡았기 때문. 지금은 60Hz 로 다 돌리고도 더 가볍다.
작업 중간에 같은 30Hz 조건으로 잰 값은 평균 3.43ms 였다 (메달 · 상태 기호를 고치기 전).

한 일 (화면 모양은 그대로):

- **상태 기호(화상 · 방어 깎기 …)**: 부대마다 매 프레임 원 · 고리 · 기호를 다시 그렸다 (프레임당 0.9ms —— HUD 에서 가장 무거웠다) → 메달 노드(`Hud.MedalNode`)가 바뀔 때만 그린다. 메달 틀 · 얼굴 · 이름표도 같은 노드 —— 매 프레임 자리 · 투명만 바꾼다. 머리표 1.55 → 0.59ms
- **삽화 병사**: 병사마다 키 11개 사전 + 람다 정렬 → 묶음 배열(`_figs`) + 정수 키 정렬 + 투영 캐시(`_pm`). 삽화 그리기는 30Hz 로 돌 때 프레임당 1.53ms 였는데, 60Hz 로 돌려도 1.12ms
- **부대 표식 · 먼지**: 부대마다 7번 그리던 것을 전 부대 묶어 4번 (`_mark_batch`)
- **접촉선**: 부대 수 제곱 계산을 부대마다 엇갈려 네 프레임에 한 번
- **바닥**: 화면 전체 픽셀마다 잡음(fbm)을 4~6번 돌던 셰이더를 매 프레임 그리지 않고 한 번만 구워 깐다 (`_ground_port` → `_ground_view`). 값이 바뀔 때만 다시 —— 삽화 화면은 카메라가 고정이라 전투마다 한 번. 휴대폰 GPU 몫
- **아래 카드**: 면 → 초상 → 글씨 순서로 모아 그려 묶음이 덜 끊긴다
- **메달 밀어내기**: 세 프레임에 한 번만 다시 푼다
- **부하 단계**: 삽화는 바닥 0. 휴대폰은 2단계(삽화 · HUD 갱신 30Hz, 화면은 60Hz)에서 시작해 프레임이 남으면 내려간다

### 전투 시작 멈춤 (혼자 하기)

혼자 하기는 전투를 시작할 때 한 판을 통째로 계산한다 (PC 약 0.57초 —— 휴대폰은 몇 초 멈춤). 온라인은 서버가 계산하므로 해당 없다.

- **계산을 스레드로** (`BattleView.async_sim`, `_simulate_async`): 계산이 도는 동안 「전투 준비 중…」 덮개를 띄우고 화면은 계속 그린다. 결과는 같은 식 · 같은 시드라 글자 하나 다르지 않다.
  함께 쓰는 지연 캐시(`DB.passives_of` · `Battle.minor_kind` · `st_kinds_of`)는 스레드를 띄우기 전에 채우고, 계산 중에는 전투장수창의 시작 능력치를 재지 않는다.
  점검 `tests/async_sim`: 결과 동일 · 계산 중 86프레임 그림(가장 긴 프레임 78ms, 예전에는 계산 시간 전체가 멈춤) · 계산 도중 온라인 재생이 들어오면 그쪽이 남는다
- **계산 자체**: 결과가 같은 범위에서만 줄였다 (원거리 목표 찾기의 먼 적 거르기 · 진영별 적 목록 한 번 · 게이지가 안 찬 부대는 고유기 가능 여부를 묻지 않기). 570 → 543ms, `algo_audit` 결과 지문 동일.
  더 줄이려면 사건마다 전 부대 상태를 복사하는 기록 형식(재생 · 서버 형식)까지 같이 봐야 한다

## 3. 전투 알고리즘

새 점검 `tests/algo_audit` —— 같은 덱 · 시드 묶음을 진영을 바꿔 두 번씩 돌려 이동 품질과 결과를 잰다 (`--n` · `--v2=0` 예전 이동 · `--bits` · `--fair=0` 예전 순서 · `--mirror` 같은 덱끼리 · `--shard`).
엔진에 세기만 하는 계측(`RtBattle.algo_probe`)을 넣었다 —— 판정 · 난수 · 사건은 그대로.

### 3-1. 이동 (`RtBattle.algo_v2`, `algo_bits` 기본 5)

240판 (진영 교체) 기준:

| | 예전 | 지금(①+③) |
|---|---:|---:|
| 원거리가 아군에 막혀 서 있는 시간 (부대 합, 판당) | 51.0초 | **25.1초** |
| 원거리: 준비가 찼는데 닿는 적이 없어 노는 시간 | 31.8% | **25.6%** |
| 근접: 같은 것 | 24.0% | 22.5% |
| 근접이 막혀 서 있는 시간 | 9.9초 | 8.2초 |
| 전투 길이 | 36.8초 | 35.7초 |
| 원거리 행동 수 (판당) | 226 | 239 |

진영 치우침(3-2)을 고친 최종 코드로 다시 잰 480판도 같다: 원거리 막힘 52.1 → 24.4초 · 원거리 노는 시간 31.8 → 25.3% · 근접 23.1 → 22.1% · 길이 37.3 → 36.1초.
| 병종별 장수당 피해 | —— | ±3% 안 |

- ① **비켜 가기 관성** —— 비켜 갈 쪽을 한 번 고르면 그 길이 막힐 때까지 지키고, 막힘이 풀린 뒤 0.5초는 같은 쪽 성분을 줄여 가며 푼다 (틱마다 더 트인 쪽을 다시 골라 좌우로 꺾이던 것)
- ③ **원거리 다가서기** —— 앞 아군 60px 뒤에서 멈추던 것을 12px 틈까지 붙는다. 그래도 막히면 기다리는 시간 3초 → 1.2초
- ② **가는 쪽 보기**(끔, 코드는 둠) —— 옆걸음 28.5 → 22.5%(근접만) / 8.5%(원거리 포함)로 줄지만 갈지자(판당 12.5 → 17.7회)와 원거리 막힘이 늘어 손익이 엇갈린다. 삽화 화면은 병사 그림이 가는 쪽을 보게 이미 처리돼 있다

토벌 난이도(자동 진행 10판씩): 토벌 승 37 → 36, 평균 도달 페이즈 9.0 → 8.8 —— 편차 안.

### 3-2. 진영 치우침 —— 고쳤다 (`RtBattle.fair_order`)

**같은 덱 · 같은 진형끼리 붙이면 A 진영이 67.2% 이겼다** (480판). 온라인 대전은 한쪽이 늘 A 다.

원인 가르기 (거울 대전 960판씩, 표준편차 약 1.6%p): 그대로 64.7% · **고유기 끔 48.4%** · 특기 · 위세 · 인연 끔 53.7% → 고유기 쪽.

- **본체: 고유기 선수.** 행동 사이마다(`Battle._between`) 양쪽 AI 가 고유기를 쓸지 정하는데 늘 A 가 먼저였다. 한쪽이 기를 모으기 시작하면
  전역 간격(`ult_gap` 2.5초) 동안 양쪽 다 못 쓰므로, 둘 다 준비된 순간마다 A 가 자리를 잡고 B 는 밀렸다.
  → `_camp_order()`: **고유기를 더 오래 못 쓴 진영이 먼저 정한다.** 같으면(개전 직후) 시드 · 행동 번호 해시
- **곁가지: 틱 처리 순서.** 부대를 A 전부 → B 전부 순서로 움직이고 행동시키던 것을 진영을 번갈아 세운 순서로, 먼저 하는 진영은 시드 · 틱 번호 해시로 (`_tick_units()`). 이것만으로는 58~64% 가 남았다
- 전투 난수(rng)는 건드리지 않는다 —— 같은 시드면 같은 결과 (determinism 30판 통과)

| | 고치기 전 | 고친 뒤 |
|---|---:|---:|
| 거울 대전 A 승률 | 67.2% (480판) | **48.1%** (960판) |
| 서로 다른 덱, 진영만 바꿔 A 승률 | 54.7% (360판) | **49.0%** (480판, 예전 이동 알고리즘으로는 49.8%) |

혼자 하기(내가 늘 A)는 그동안 이 덕을 봤다. 자동 진행 10판의 토벌 승수 · 도달 페이즈는 전후가 같았다 (토벌은 고유기가 드문 낮은 등급이 많다).

## 5. 주의
